# mcp-server (`@devdigest/mcp-server`)

## Overview

A local, stdio MCP server for DevDigest. It is a thin HTTP client of the
Fastify API on `:3001` — no DB access, no business logic of its own, no
imports from `server/src` beyond the `@devdigest/shared` contract alias (the
repo's sanctioned cross-package sharing mechanism). It exposes exactly 5
tools: `list_agents`, `run_agent_on_pr`, `get_findings`, `get_conventions`,
`get_blast_radius`.

`list_repos`/`list_prs` are deliberately NOT exposed — `gh` or GitHub's own
MCP server already cover repo/PR discovery. Every tool here instead takes a
human-legible `{repo: "owner/name", pr_number}` (and `agent` for the run
tool) and resolves it to this app's internal uuids via `src/api/resolve.ts`.

## Commands

- `npm install` once before first use.
- `npm run dev` / `npm start` — runs `tsx src/index.ts` directly. **No build
  step** — this is a short-lived CLI process spawned by an MCP client, not a
  long-running server, so there's nothing to compile ahead of time.
  **`start` is deliberately plain `tsx`, never `tsx watch`** — a watch-mode
  restart mid-session would tear down the stdio JSON-RPC connection the
  client is relying on.
- `npm test` — vitest, hermetic (stub `fetchImpl` / in-memory MCP transport,
  no real network, no keys).
- `npm run typecheck` — `tsc --noEmit`.
- `npm run lint` — flat config; `no-console: error` is a hard lint rule here
  (see Conventions).

## Conventions

- **npm, not pnpm** — like `reviewer-core/`/`e2e/`, this is a short-lived CLI
  process, never part of the `server`/`client` web boot. Using pnpm here
  would create a competing lockfile.
- **Package-manager split mirrors the rest of the repo**:
  `server`/`client` → pnpm; `reviewer-core`/`e2e`/`mcp-server` → npm.
- **The 5-tool ceiling is a hard design constraint**, not a current count to
  grow casually. Adding a 6th tool is a deliberate decision, not a default.
- **stdout is owned end to end by the JSON-RPC stdio transport.** All
  logging goes to stderr via `src/log.ts`; `console.*` anywhere in this
  package is a lint error (`no-console: error` in `eslint.config.mjs`), not
  just a style nit — a stray stdout write corrupts the protocol stream.
- **Never log response bodies or finding text** — `LogFields` (`src/log.ts`)
  is deliberately flat (`string | number | boolean | null`, no nested
  objects/arrays) so a body or finding can't be passed as a log field
  without a TypeScript error.
- **Config is env-vars only** — no `.env` file, no secrets. See the env-var
  table in `README.md`.
- **The resolver (`src/api/resolve.ts`) is internal and deliberately
  uncached.** Two extra loopback GETs per tool call is cheaper than a
  stale-repo-list bug. This is a stated non-goal, not a TODO.
- **Every tool response is validated against its `@devdigest/shared` Zod
  contract** (the same contracts the API itself serializes through) before
  the tool shapes its reply — `src/api/client.ts` never trusts an
  unvalidated JSON body.
- Entrypoint discipline: `src/index.ts` is the ONLY module allowed to call
  `process.exit`. Every other module throws (`ConfigError`, `ApiError`,
  `ResolveError`) so it stays unit-testable without a child process.

## Do not touch

- `package-lock.json` — generated by `npm install`; never hand-edited.
- Must never import `server/src` beyond the `@devdigest/shared` contract
  tree (`../server/src/vendor/shared`) — no business logic duplication, no
  reaching into server internals.
- Must never touch the DB directly, and must never call a write/LLM
  server endpoint from a read-only tool (`get_findings`, `get_conventions`,
  `get_blast_radius`, `list_agents` are read-only; only `run_agent_on_pr`
  writes).

## Gotchas

- The MCP SDK's `registerTool` generic overloads blow up TypeScript's
  instantiation-depth limit (`TS2589`) if `tsconfig.json`'s `paths` maps the
  bare `"zod"` specifier to an explicit `./node_modules/zod` path — drop
  that mapping (keep only the `@devdigest/shared` alias); the ambient
  resolution already finds the right `zod` without it. Passing a raw
  `z.object({...}).strict()` instance as `inputSchema` (rather than
  `.shape`) is fine either way; the `zod` path alias was the actual trigger.
- `GET /pulls/:id/runs`' `RunSummary` fields are all required keys even
  though most are `.nullable()` (not `.nullish()`) — a test fixture missing
  one (e.g. `provider`, `tokens_in`) fails `safeParse` silently as an
  `ApiError` surfaced through the tool's generic catch, which reads like an
  unrelated failure. Build fixtures from a single "every field present,
  defaulted to `null`" helper (see `run-agent-on-pr.test.ts`'s `runSummary`)
  rather than hand-rolling partial objects per test.
- Vitest/Vite doesn't read `tsconfig.json`'s `paths` on its own — mirror the
  `@devdigest/shared` alias in `vitest.config.ts`'s `resolve.alias` too (see
  `reviewer-core/vitest.config.ts`, same root cause).
- `GET /pulls/:id/runs` (`RunSummary.status`) is the only authoritative
  status source for a run — `GET /runs/:id/trace` (`RunTrace`) has no
  top-level `status` field, so the `run_agent_on_pr` poller must never use
  it to decide when a run is done.
