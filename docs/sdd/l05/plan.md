- `server/AGENTS.md`, `server/docs/architecture.md`: static plugins; route → service → repository; adapters behind container; schema-first request/response validation. SQL belongs in repositories.
- `server/specs/review-flow.md`, `server/INSIGHTS.md`: preserve run persistence order and `RunLogger` signature. Existing server tests live under `server/test/`; DB tests require `.it.test.ts`.

- `client/AGENTS.md`, `client/docs/ui-architecture.md`: hooks over `api.ts`, thin pages, colocated PascalCase component folders/barrel/styles/tests, English message keys.
- Both vendored contract copies change together under one owner. Avoid unrelated drift repairs.
- `reviewer-core/AGENTS.md`, `reviewer-core/specs/review-engine.md`: no filesystem/database I/O; preserve grounding and injection guard.
- `repo-intel/README.md`: consume persisted index only; new callers must not invoke legacy missing-index code-scanning fallback.
- Reuse existing `pr_brief` and `onboarding` JSON tables. Metadata columns need a generated migration; attachment bodies belong only in separate run snapshots.
- Skill routing comes from `.claude/skills/pr-self-review/SKILL.md`. Use the user-authorized `l04/mcp` baseline when reviewing changes.
- **Tokenizer, confirmed at this baseline (resolves finding D2 — was previously an unverified assertion)** — `server/src/adapters/tokenizer/index.ts`: the `Tokenizer` interface (lines 16–18) exposes exactly `count(text: string): number`, nothing else. `TiktokenTokenizer` (lines 25–39) lazily loads `js-tiktoken`'s `cl100k_base` encoding (line 32); on any load/encode failure it sets a sticky `broken` flag and falls back to the `ceil(chars/4)` heuristic (`approxTokens`, lines 21–23; fallback wiring lines 34–38) for every subsequent call — it does not retry the real encoder per call once broken. TASK-04 adds estimate/encoding metadata on top of this exact existing surface; it must separate estimated input from provider-reported usage rather than assuming the current adapter already distinguishes them.
- **Repo-intel rank/hotness, confirmed at this baseline (resolves finding D2)** — `server/src/modules/repo-intel/service.ts`: `getFileRank(repoId, paths)` (lines 418–422) returns `Promise<FileRankRow[]>`; `FileRankRow` (`types.ts` lines 119–122) is `{path: string, percentile: number}` — not raw rank, not hotness. `getTopFilesByRank(repoId, n, opts?)` (lines 639–655) returns `Promise<string[]>` — paths only, over-fetched 10× then filtered (junk-path exclusion, caller `exclude` substrings) and truncated to `n`. Neither method exposes the raw `rank` or `hotness` columns the indexer actually persists per file (`IndexerFileRankRow`, `repository.ts` lines 90–96: `{filePath, pagerank, hotness, rank, percentile}`). `hotness` is currently **hardcoded to `0` for every row** (`pipeline/rank.ts` lines 5–6/51; `pipeline/full.ts` line 262; `pipeline/incremental.ts` line 251 — "Option B": PageRank only, shallow `CLONE_DEPTH=1` clone, no churn window) — so TASK-07's "disclose absent hotness" path is the *common* case at this baseline, not an edge case to merely handle defensively. TASK-07 must add a new narrow facade method that exposes the raw `rank`/`hotness` columns directly rather than reusing `getFileRank`/`getTopFilesByRank`'s existing, narrower return shapes.
